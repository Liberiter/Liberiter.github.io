2의 보수를 구하는 방법은 알고 있었습니다. 비트를 뒤집고 1을 더한다. 모르던 건 **왜
그게 되는가**였고, 증명을 따라가 보니 세 줄로 끝나더군요. 그리고 그 세 줄을 잡아당기니
음수 표현 전체가 딸려 나왔습니다.

## 나머지를 역순으로 쓰면 왜 2진수가 되는가

`1101`이라는 표기가 뜻하는 건 이겁니다.

```
N = d_0·2^0 + d_1·2^1 + d_2·2^2 + ...      (d_i ∈ {0, 1})
```

진법 표현 정리에 따르면 모든 음이 아닌 정수는 이런 표현을 갖고, 그 표현은 유일해요.
유일하다는 게 중요한데, 우리가 찾아낸 답이 곧 그 답이라는 보장이기 때문입니다.

전개식을 `d_0` 기준으로 묶어 봅니다.

```
N = d_0 + 2·(d_1 + d_2·2 + d_3·2^2 + ...)
```

괄호 안을 `Q`라고 부르면 `N = 2Q + d_0` 꼴이 됩니다. 나눗셈 정리는 "N을 2로 나누면
몫과 나머지가 유일하게 결정된다"고 말하고, 위 식이 정확히 그 꼴이면서 `0 ≤ d_0 < 2`를
만족해요. 유일성에 의해 **N을 2로 나눈 나머지는 다름 아닌 `d_0`입니다.** 우연히 같은 게
아니라 그것 말고 다른 답이 있을 수 없어요.

몫 `Q`는 원래 수의 자릿수를 한 칸 밀어낸 수입니다. `d_1`이 새로운 1의 자리에 앉아 있죠.
같은 논리를 적용하면 나머지는 `d_1`, 또 나누면 `d_2`가 나옵니다.

나눗셈 한 번은 **맨 아래 자릿수를 뜯어내고 나머지를 한 칸 내리는** 연산이에요. 비트로
보면 오른쪽 시프트고, 나머지는 밖으로 떨어지는 그 비트입니다.

```
13 ÷ 2 = 6 … 1     ← d_0
 6 ÷ 2 = 3 … 0     ← d_1
 3 ÷ 2 = 1 … 1     ← d_2
 1 ÷ 2 = 0 … 1     ← d_3
```

역순으로 쓰면 `1101`. 검산하면 `8 + 4 + 0 + 1 = 13`입니다.

역순으로 뒤집는 이유는 허무할 만큼 단순해요. **알고리즘은 아래 자리부터 뽑는데 우리는
숫자를 위 자리부터 쓰기 때문입니다.** 트릭이 아니라 표기 관습과 생성 순서가 반대라서
생기는 정리 작업이에요.

그리고 이 논증에서 2를 `b`로 바꿔도 한 글자도 안 틀립니다. `N = bQ + d_0`. 10진수를
7로 계속 나누면 7진수가 나와요.

## 증명: 뒤집고 1을 더하면 2^n − x

먼저 2의 보수의 사전적 의미부터 정리하면, **어떤 수를 2^n에서 뺀 값**이 맞습니다.
다만 `n`은 아무 값이나가 아니라 **워드 폭**이에요. 8비트로 일하면 `n = 8`로 고정입니다.

이건 2진법 전용 개념도 아닙니다. 일반적으로 기수 보수(radix complement)라는 게 있어요.

| 이름 | 정의 | 2진법에서 | 10진법에서 |
|---|---|---|---|
| 기수 보수 | `b^n − x` | 2의 보수 | 10의 보수 |
| 감수 기수 보수 | `(b^n − 1) − x` | 1의 보수 | 9의 보수 |

"2의 보수"의 2는 개수가 아니라 **기수**입니다. 그리고 아래 줄이 diminished(감소된)인
이유가 보이는데, 정확히 1만큼 작아요. 이게 증명의 전부입니다.

**보조정리.** n비트 수 `x`의 비트를 `x_0 … x_{n-1}`이라 하면, 뒤집은 수 `~x`의 각 비트는
`1 − x_i`입니다.

```
~x = Σ(1 − x_i)·2^i = Σ2^i − Σx_i·2^i = (2^n − 1) − x
```

`Σ2^i`는 등비급수라서 `2^n − 1`이고, 뒤는 그냥 `x`예요.

**정리.** 양변에 1을 더합니다.

```
~x + 1 = (2^n − 1) − x + 1 = 2^n − x
```

`~x`는 그 자체로 1의 보수입니다. 보조정리가 정확히 1의 보수의 정의거든요. 그리고 1의
보수는 2의 보수보다 정확히 1 작습니다. "뒤집고 1 더하기"는 외울 규칙이 아니라 **그 한
칸을 메우는 동작**이에요.

8비트로 확인해 봅니다.

```
x       = 00000101   (5)
~x      = 11111010   (250 = 255 − 5)   ← 1의 보수
~x + 1  = 11111011   (251 = 256 − 5)   ← 2의 보수
2^8 − 5 = 251                          ← 직접 계산해도 같다
```

## 이건 2진법만의 우연이 아니다

증명이 아름답다고 느꼈는데, 알고 보니 우연이 전혀 아니었습니다. **모든 진법에서 똑같이
성립하는 정리**예요. 위 증명에서 2를 `b`로 바꾸기만 하면 됩니다.

```
y_i = (b−1) − x_i
y   = Σ(b−1)·b^i − Σx_i·b^i = (b^n − 1) − x
y+1 = b^n − x
```

10진법으로 눈으로 확인해 보세요. `x = 347`, `n = 3`입니다.

```
  999      ← 10^3 − 1, 모든 자리가 9
- 347         빌림 없음: 9−3, 9−4, 9−7
-----
  652      ← 9의 보수
+   1
-----
  653 = 1000 − 347
```

뒤집고 1 더하기의 10진법 버전이고, 하는 일이 완전히 같습니다.

빌림이 없는 이유도 진법과 무관해요. 감수의 모든 자릿수가 `b−1`, 즉 가능한 최댓값이라서
어떤 `x_i`를 빼도 모자라지 않습니다.

**그럼 2진법이 특별한 건 뭘까요.** 정리가 아니라 **비용**입니다.

| 진법 | 자릿수 변환 | 구현 비용 |
|---|---|---|
| 10진 | `d → 9−d` | 조회표 또는 뺄셈기 |
| 16진 | `d → F−d` | 조회표 |
| 2진 | `d → 1−d` | NOT 게이트 하나 |

2진법에서는 자릿수가 `{0, 1}` 둘뿐입니다. 두 원소 집합 위의 자기역함수는 항등함수
아니면 맞바꿈 둘뿐이고, 우리가 원하는 건 맞바꿈이니 선택의 여지 없이 부정(NOT)이 돼요.
정리는 어디에나 있는데 공짜인 곳은 여기뿐입니다.

## 1의 보수는 국소적이고 2의 보수는 전역적이다

이름이 왜 저런지가 두 개념의 성격 차이를 그대로 보여줍니다.

```
1의 보수:  x_i + y_i = 1     자릿수마다
2의 보수:  x   + y   = 2^n   수 전체에 대해
```

`00000101`과 `11111010`을 세로로 겹쳐 놓고 자리마다 더해 보세요. 어느 자리든 합이 1이라
**1의 보수**입니다. 반면 `00000101 + 11111011 = 100000000 = 2^8`이라, 수 전체를 다 더해야
기수의 거듭제곱이 나와서 **2의 보수**예요.

이 국소/전역 구분이 곧 비용 구분입니다. 국소적 보수는 자리끼리 대화할 필요가 없어서
병렬로 한 사이클에 끝나지만, 전역적 보수는 자리들이 빌림으로 소통해야 해서 전파 지연이
생겨요.

실제로 `2^n − x`를 곧이곧대로 하면 이렇게 됩니다.

```
  100000000      ← 이 자리에서 빌려오면
- 000000101         빌림이 아래로 줄줄이 전파된다
```

반면 `(2^n − 1) − x`는 감수의 모든 자리가 1이라 빌릴 일이 아예 없습니다. 각 비트가
독립적으로 `1 − x_i`, 즉 NOT 게이트 하나예요.

**어려운 쪽을 포기하고 공짜인 쪽을 한 다음 1을 더하는 겁니다.** 그 +1조차 공짜인데,
어차피 뺄셈은 덧셈기로 들어가니 가산기의 캐리 입력에 1을 넣으면 끝나거든요.

전부 압축하면 `999 + 1 = 1000`입니다. 2진법으로 쓰면 `111 + 1 = 1000`이고요. 초등학교에서
배운 사실이 CPU 뺄셈 회로의 근거예요.

## 왜 2의 보수를 음수라고 부르는가

컴퓨터공학이 그렇게 정의한 게 아니라, 그렇게 될 수밖에 없는 걸 발견하고 이름만 붙인
겁니다.

**n비트 레지스터는 이미 `Z/2^nZ`입니다.** 8비트 레지스터에 담을 수 있는 패턴은 256개뿐이라
`200 + 100 = 300`을 하면 담을 데가 없어요. 넘친 비트가 떨어지고 44가 남습니다.

```
200 + 100 = 300 ≡ 44 (mod 256)
```

캐리를 버리는 순간 그 회로는 `mod 2^n` 산술을 하고 있는 거예요. 안 버리려면 무한
레지스터가 필요하니 다르게 만들 방법이 없습니다.

환에서 음수의 정의는 하나뿐입니다. **`−x`는 `x`에 더해서 0이 되는 원소**예요.

```
x + y ≡ 0 (mod 2^n)
```

`0 ≤ x, y < 2^n`이니 `x + y`는 0과 `2^{n+1}` 사이인데, 이 범위에서 `2^n`의 배수는 0과
`2^n`뿐이고 `x ≠ 0`이면 `x + y = 0`은 불가능합니다. 따라서 `y = 2^n − x`. 그리고 이
`y`는 유일해요. 다른 `y'`도 조건을 만족하면 `y ≡ −x ≡ y'`이니까요.

**2의 보수를 음수로 정한 게 아니라, `mod 2^n` 세계에서 `−x`가 원래부터 `2^n − x`입니다.**
덧셈 역원은 하나뿐이라 고를 여지가 없었어요.

`x = 0`일 때도 `y = 2^n ≡ 0`이라 0의 역원이 0 자신입니다. `−0` 문제가 안 생기는 게
운이 좋아서가 아니라 이 때문이에요.

## 진짜 선택은 창을 어디에 놓느냐였다

환 자체에는 부호라는 게 없습니다. `Z/256Z`에서 `11111011`은 251이자 −5인데, 둘 중
뭐냐고 물으면 답이 없어요. **같은 원소**거든요. `251 ≡ −5 (mod 256)`은 "같은 값으로
취급한다"가 아니라 문자 그대로 같다는 뜻입니다.

그래서 실제로 한 선택은 하나뿐이었습니다. 256개 원소 중 **어디까지를 음수라고 부를지**.

| 해석 | 대표원 창 |
|---|---|
| unsigned | `0 ~ 2^n − 1` |
| signed | `−2^{n−1} ~ 2^{n−1} − 1` |

같은 환, 같은 비트, 같은 회로에 창만 다릅니다. 재밌는 건 산술만 따지면 창을 어디에 놔도
상관없다는 거예요. 완전잉여계이기만 하면 덧셈, 뺄셈, 곱셈이 전부 맞게 돌아갑니다.

**정확히 반으로 자른 이유는 부호를 최상위 비트 하나로 읽기 위해서예요.** 창을
`[−2^{n−1}, 2^{n−1})`로 잡을 때만 `x < 0 ⟺ MSB = 1`이 성립하거든요. 조금이라도
어긋나면 부호 판정에 비교 연산이 필요해집니다.

## 하드웨어가 이걸 증언한다

x86 명령어 집합을 보면 어디까지가 환 연산이고 어디부터가 해석인지 그대로 갈려 있습니다.

| 연산 | signed/unsigned |
|---|---|
| 덧셈 `ADD`, 뺄셈 `SUB` | 명령이 하나뿐 |
| 곱셈 하위 n비트 | 같다 |
| 곱셈 상위 n비트 | 다르다 (`MUL` / `IMUL`) |
| 나눗셈 | 다르다 (`DIV` / `IDIV`) |
| 오버플로 플래그 | 둘 다 있다 (`CF` / `OF`) |
| 비교 분기 | 둘 다 있다 (`JB/JAE` / `JL/JGE`) |

덧셈에 signed 버전이 없는 건 필요가 없어서입니다. 환 연산이 하나뿐이니까요. 컴파일러가
`int`를 더하든 `unsigned`를 더하든 똑같은 `ADD`를 뱉습니다. 곱셈 하위 비트가 같은 것도
곱셈이 환 연산이기 때문이고요.

나눗셈만 진짜로 다른 이유는 나눗셈이 `Z/2^nZ`의 연산이 아니라서입니다. 이 환은 체가
아니라 나눗셈이 잘 정의되지 않아요.

`10000000 + 10000000`은 계산 결과가 하나인데, unsigned로는 자리넘침(`CF`)이고 signed로는
`−128 + −128`이 창을 벗어난 것(`OF`)입니다. 같은 사건에 이름이 둘이에요.

## 부호 확장

`11111011`(8비트 −5)을 16비트로 늘릴 때 앞을 1로 채우는 이유도 창에서 따라 나옵니다.

MSB가 1인 n비트 패턴의 값은 `S = U − 2^n`이에요. 앞을 1로 채워 m비트로 늘리면:

```
U' = U + (2^m − 2^n)
S' = U' − 2^m = U − 2^n = S
```

0으로 채우면 `S' = U`가 되어 정확히 `2^n`만큼 어긋납니다. −5가 251이 돼 버려요.

## 캐리를 버리는 게 수학적으로 정당한가

여기가 가장 오래 걸렸던 의문입니다. 35의 10의 보수인 65를 그 수의 음수라고 생각하지는
않잖아요. 컴퓨터가 캐리를 버려서 0을 만드는 게 편법 아닌가 싶었습니다.

**결론은 반쯤 맞습니다.** 산술은 완벽히 정당하고, 정당하지 않은 건 딱 하나예요.

먼저 `Z`에서는 `65 ≠ −35`가 맞습니다. 그런데 `Z/100Z`에서는 `65 = −35`예요. `65 + 35 =
100 = 0`이니까요. 65를 −35로 안 느끼는 이유는 무의식중에 자릿수 제한이 없는 세계에 있기
때문입니다. 6자리 주행거리계가 `000000`에서 1km 후진하면 `999999`가 되는데, 아무도 이걸
이상하다고 하지 않아요. 그릇이 유한하다는 걸 눈으로 보고 있으니까요.

**캐리를 버리는 연산에는 이름이 있습니다.**

```
π: Z → Z/2^nZ
```

몫환으로의 표준 사영(canonical projection)이고, 학부 대수학 첫 장에 나오는 물건이에요.
가우스가 1801년에 합동식을 정리하면서 이미 있던 겁니다. 그리고 `π`는 환 준동형이라
`π(a+b) = π(a)+π(b)`, `π(ab) = π(a)π(b)`가 성립해요. 이 두 줄이 하드웨어 정당성의
전부입니다. 중간에 매번 캐리를 버려도 최종 답이 맞는다는 보장이거든요.

**그런데 `π`가 보존하지 못하는 게 하나 있습니다. 순서예요.**

`Z/2^nZ`에는 순서를 줄 수 없습니다. 안 준 게 아니라 불가능해요. 덧셈과 호환되는 전순서가
있다고 하고 `x > 0`인 원소를 잡으면, 호환성에서 `x + x > x > 0`이고 반복하면 임의의 `k`에
대해 `kx > 0`입니다. 그런데 `2^n·x = 0`이니 `0 > 0`이라는 모순이 나와요. **유한환은 순서를
가질 수 없습니다.**

그래서 `11111011`이 251보다 큰지 −5보다 큰지 묻는 질문 자체가 성립하지 않습니다. 대소를
쓰려면 바깥에서 억지로 부과해야 하고, 부과하는 방법이 둘이라 비교 명령도 둘이에요.
`ADD`는 하나인데 `JB/JAE`와 `JL/JGE`가 따로 있는 이유가 이겁니다.

의심이 향한 방향은 옳았는데, 겨눌 자리가 산술이 아니라 순서였던 거예요.

## 수학에도 2의 보수가 있다

`…1111이 −1이다`라는 표현이 실제로 존재하는 수학 체계가 있습니다. 컴퓨터보다 먼저
나왔고요.

1897년 쿠르트 헨젤이 만든 **p진수**입니다. 2진 정수 `Z_2`에서는 이게 성립해요.

```
−1 = …11111111
```

비유가 아니라 등식입니다. 유한 자릿수에서 `11…1`(n개)은 `2^n − 1`인데, `n → ∞`로 보내면
`2^n − 1 → −1`이어야 해요. 보통 거리로는 `2^n`이 발산하지만 **2진 거리에서는 `2^n → 0`**
입니다. p진 거리는 2로 많이 나누어떨어질수록 0에 가깝다고 재거든요.

−5를 2진 정수로 쓰면 `…11111011`이고, 우리가 8비트로 구한 `11111011`이 이것의 끝
8자리입니다.

```
n비트 2의 보수 = 2진 정수를 n자리에서 자른 것
Z/2^nZ = Z_2 / 2^n·Z_2
```

부호 확장의 정체도 여기서 드러납니다. 앞을 1로 채우는 건 **잘라낸 무한 꼬리를 도로
복원하는 것**이에요. −5의 진짜 모습이 `…111111011`이니 규칙을 지어낸 게 아닙니다.

정수론자들이 컴퓨터 없던 시절에 만든 표기를 컴퓨터가 유한 자릿수로 잘라 쓰고 있는
셈인데, 헨젤은 CPU를 생각한 적이 없고 폰 노이만 세대는 p진수를 참고한 적이 없어요.
같은 구조에 양쪽에서 독립적으로 도달한 겁니다.

## `1000`의 2의 보수가 `1000`인 이유

4비트에서 이런 게 나옵니다.

```
x      = 1000
~x     = 0111
~x + 1 = 1000      ← 자기 자신
검산: 2^4 − 8 = 8
```

4비트 창은 `[−8, 7]`이니 `1000`은 −8이고, 따라서 `−(−8) = −8`이에요.

**예외처럼 보이지만 이런 수는 하나가 아닙니다.** 방정식을 풀면 됩니다.

```
x ≡ −x (mod 2^n)
2x ≡ 0 (mod 2^n)
x = k·2^{n−1}       →  0 ≤ x < 2^n 에서 x = 0 또는 x = 2^{n−1}
```

**해가 정확히 둘이고, 나머지 하나는 0입니다.** `−0 = 0`은 당연하게 느껴져서 눈에 안
띄었을 뿐이에요. `1000`이 이상하게 느껴진 건 특이해서가 아니라 0과 똑같은 성질을 가졌는데
0처럼 안 생겨서입니다.

왜 정확히 둘인지는 세 가지로 설명됩니다.

**개수를 세면 나옵니다.** 패턴이 `2^n`개로 짝수인데 0을 빼면 `2^n − 1`개, 홀수가 남아요.
`{x, −x}` 짝으로 묶으면 홀수는 짝을 다 못 지어서 반드시 하나가 남고, 남은 그것은 자기
자신과 짝지을 수밖에 없습니다. `[−128, 127]`이 비대칭인 게 설계 실수가 아니라 개수 세기의
결과예요. 대칭으로 만들려면 홀수 개를 짝수 개로 만들어야 하는데 불가능합니다.

**원 위의 반사로 봐도 됩니다.** `2^n`개 원소를 시계처럼 원에 둘러놓으면 `x → −x`는 0을
지나는 축에 대한 반사예요. 원을 반사하면 축이 뚫고 지나가는 두 점만 제자리에 남는데,
하나는 0이고 다른 하나는 0의 대척점입니다. 12시간 시계에서 `−x ≡ 12 − x`를 풀면
`x ∈ {0, 6}`이 나와요. 6시의 반대 방향은 6시입니다.

**군론으로는 피할 수 없다는 게 증명됩니다.** `(Z/2^nZ, +)`는 위수 `2^n`인 순환군이고,
`x = −x`인 원소는 위수가 2 이하인 원소예요. 순환군은 각 약수마다 부분군을 정확히
하나씩 갖는데, `2^n`이 짝수라 위수 2인 부분군이 정확히 하나 존재하고 그게
`{0, 2^{n−1}}`입니다.

`−(−8) = 8`이라는 계산 자체는 정확합니다. 문제는 4비트 창 `[−8, 7]`에 8이 없다는 거예요.
계산이 틀린 게 아니라 답을 적을 자리가 없습니다.

## 컴퓨터는 이걸 어떻게 해결하는가

해결하지 않습니다. 하드웨어는 **정확히 계산하고 창을 넘었다고 신고만** 해요.

```
NEG 1000
→ 결과: 1000     환에서 정확한 답
→ OF = 1         "창 넘었음" 신고
```

실행 중에 비트 폭이 늘어나는 일은 없습니다. 4비트 레지스터는 언제나 4비트예요. 폭은
명령어와 타입이 컴파일 시점에 못박습니다.

**하드웨어가 안 고치는 이유는 의미를 모르기 때문입니다.**

| 그 숫자가 무엇이냐 | 오버플로 시 맞는 행동 |
|---|---|
| 잔액 | 터져야 한다 |
| 오디오 샘플 | 포화(clamp). 트랩하면 음악이 멈춘다 |
| 픽셀 밝기 | 포화. 감싸면 밝은 부분이 검게 뒤집힌다 |
| 해시값 | 감싸야 한다. 그게 설계 의도다 |
| 암호 연산 | 감싸야 한다. 분기하면 타이밍이 샌다 |

`ADD` 회로는 그 32비트가 돈인지 픽셀인지 알 방법이 없어서 고를 수가 없어요. 어떤 ISA는
아예 선택을 명령어로 내주는데, MIPS의 `add`는 오버플로에 트랩하고 `addu`는 조용히
감쌉니다.

실제 대응은 다섯 가지입니다.

| 전략 | 4비트 `−(−8)` | 쓰는 곳 |
|---|---|---|
| 감싸기 | −8 | C unsigned, Java, 해시, 암호 |
| 트랩 | 예외 / panic | Rust 디버그, Swift, Ada, 금융 |
| 포화 | 7 | DSP, 오디오, 이미지, SIMD |
| 정적 확장 | 8 (8비트로 승격 후) | 컴파일러 승격, 수동 캐스팅 |
| 무한 정밀도 | 8 | Python, BigInteger, GMP |

Rust가 가장 정직한데, 넷을 전부 API로 노출하고 기본값을 강요하지 않습니다.

```rust
let x: i32 = i32::MIN;

x.wrapping_neg()      // i32::MIN         감싼다
x.checked_neg()       // None             실패를 값으로 반환
x.saturating_neg()    // i32::MAX         포화
x.overflowing_neg()   // (i32::MIN, true) 결과 + 넘침 여부
```

포화는 오류 처리가 아니라 그 도메인의 정답인 경우가 많습니다. 8비트 밝기값 200에 100을
더하면 감쌌을 때 44가 되어 거의 검은색이 되지만, 포화시키면 255로 흰색이 돼요. 밝게
만들려다 검게 뒤집히는 건 재앙이고 하얗게 날아가는 건 그냥 좀 밝은 사진입니다. 그래서
SIMD에 포화 버전이 따로 있어요(x86 `PADDSB`, ARM `QADD`).

무한 정밀도에서 늘어나는 건 하드웨어가 아니라 자료구조입니다. 고정폭 조각을 배열로 들고
부족하면 힙에서 더 할당해요. 대신 하드웨어가 캐리를 소프트웨어에 노출해 줍니다
(`ADC`, `SBB`). 버려지던 캐리를 주워서 다음 조각으로 넘길 수 있어야 큰 수 연산을 만들 수
있거든요.

## 넓히는 건 해결이 아니라 연기다

`int32`가 무서워서 `int64`로 올려도 `INT64_MIN`에 똑같은 성질이 있습니다.

```
−(−2^63) = 2^63 ∉ [−2^63, 2^63 − 1]
```

`2^64`도 짝수라서 패리티 논증이 그대로 적용돼요. **폭을 늘리면 함정이 사라지는 게 아니라
더 먼 곳으로 옮겨갑니다.** `int64`가 안전해 보이는 건 함정이 없어서가 아니라 거기까지 갈
일이 잘 없어서예요.

진짜로 없애는 유일한 방법은 창을 버리는 것이고, 대가는 성능입니다. Python이 느리고 C가
빠른 이유가 여기 있어요.

참고로 이 함정이 없는 체계도 있습니다. 균형 3진법은 자릿수를 `{−1, 0, +1}`로 잡아서 음수
만들기가 전부 부호 뒤집기이고, 보수 연산도 `−0` 문제도 없으며 범위가 완벽히 대칭이에요.
`3^n`이 홀수라 `2x ≡ 0 (mod 3^n)`의 해가 0 하나뿐이거든요. 1958년 모스크바 국립대에서
Setun이라는 컴퓨터가 실제로 이 방식으로 돌아갔고, 크누스는 이걸 "아마도 모든 수 체계 중에
가장 예쁜 것"이라고 썼습니다. 밀린 이유는 세 상태를 안정적으로 구별하는 회로가 두
상태보다 훨씬 비싸기 때문이에요. 수학적으로는 3진법이 더 예뻤는데 물리적으로는 2진법이 더
쌌습니다.

## 남는 것

`INT_MIN` 함정은 2진법을 쓰는 한 영구적입니다. 더 좋은 인코딩을 찾아서 될 일이 아니라
`2^n`이 짝수인 한 구조적으로 강제돼요.

실무에서 오버플로 버그의 정체도 여기서 나옵니다.

```c
int mid = (low + high) / 2;   // 20년 넘게 살아 있던 이진 탐색 버그
```

`Z`에서는 완벽한 코드지만 `Z/2^32Z`에서는 `low + high`가 창을 넘어가면 음수가 됩니다.
기계는 자기 환에서 정확한 답을 냈고, 틀린 건 그게 `Z`의 답이라고 믿은 쪽이에요.
**프로그래머는 `Z`에서 생각하고 기계는 `Z/2^nZ`에서 계산합니다.**

정당성은 절대적인 게 아니라 어느 구조에 있다고 선언했느냐에 상대적입니다.

| | 정당한가 |
|---|---|
| 캐리 버리기 | 정당하다. 몫환 사영 |
| `2^n − x`를 `−x`로 보기 | 정당하다. 유일한 덧셈 역원 |
| 덧셈, 뺄셈, 곱셈 | 정당하다. 준동형이 보존 |
| 대소 비교 | 정당하지 않다. 유한환에 순서가 없어 밖에서 부과 |
| `Z`의 답이라고 주장하기 | 정당하지 않다. 창을 넘으면 틀린 답 |
